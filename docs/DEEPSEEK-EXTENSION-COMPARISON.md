# DeepSeek extensions for Pi: cltec and bxff

**Compared snapshots.** `cltec/pi-deepseek-search` at [`25060ca23412f340db90c619058cc4c7e07118da`](https://github.com/cltec/pi-deepseek-search/tree/25060ca23412f340db90c619058cc4c7e07118da) is private Apache-2.0 `0.1.0` in its [manifest][c-pkg]. The public npm registry reported [`pi-deepseek-search@1.2.2`][b-npm] as [`latest`][b-registry], with bxff as the project author and [`5b5f3f3f341b75ea8e3b72ec2a2e758682fd6311`](https://github.com/bxff/pi-deepseek-search/commit/5b5f3f3f341b75ea8e3b72ec2a2e758682fd6311) as `gitHead`. The MIT [tarball][b-tar] matched registry SHA-512 integrity; all six files matched that commit byte-for-byte. [bxff manifest][b-pkg]

| Area | cltec `25060ca` | bxff npm `1.2.2` |
| --- | --- | --- |
| Tools and workflow | `deepseek_web_search(query)` → `deepseek_web_fetch(url)` → `deepseek_web_read_full(ref, …)` when more text is needed. Search accepts query operators, not separate domain arguments. [Schemas and prompts][c-tools] | `web_search(query, allowed_domains?, blocked_domains?)` → `web_fetch(url)` → cite. Domain lists are optional despite the README's wording; nonempty lists are mutually exclusive and become `site:`/`-site:` query syntax, not an enforced allowlist. [README][b-readme], [schemas][b-tools], [request builder][b-domains] |
| API and auth | Both use fixed Bearer-authenticated JSON POSTs to `https://api.deepseek.com/v1/tools/search` and `/v1/tools/fetch`; neither replaces Pi's conversation model. cltec uses only those endpoints and reads `DEEPSEEK_API_KEY` at load. [README][c-start], [provider][c-provider], [key lookup][c-config] | Uses Pi's DeepSeek key first, then `DEEPSEEK_API_KEY`, then undocumented `ANTHROPIC_AUTH_TOKEN`. Optional `DEEPSEEK_SEARCH_BACKEND=server` sends an extra model request to `/anthropic/v1/messages` with `x-api-key`, defaults to `deepseek-flash` (overridable), and returns sources and token usage, not the model answer. Fetch stays standalone. [Key lookup][b-key], [backend][b-backend], [server][b-server] |
| Profiles and budgets | Global defaults: 3 search results, 12,000 display chars, no full search content; sends `count` and `need_content`. Supports active-model selectors and project overlays only with global opt-in and Pi trust. [Profiles][c-profile], [request and output][c-web], [provider][c-provider] | Standalone Search sends only `query`; the README's 10 hits/no full content describe provider defaults, not client-enforced limits. No comparable profiles or tool-output budget; the eight-line collapsed TUI preview does not cap model-visible output. [README][b-readme], [renderer][b-key], [request][b-api], [output][b-backend] |
| Retrieval and exports | Session refs page `section` with `offset`/`maxChars` (search requires one-based `resultIndex`). Fetch fields can export via `mode: "file"`, optional `path`/`overwrite`; temporary exports are cleaned up, and model-chosen explicit paths require UI approval. Bounded cache can evict data; global opt-in allows one potentially billable replay per retained ref, matching search URLs by occurrence. Replayed content may differ. [Contract][c-retrieval], [approval][c-tools], [cache and replay][c-cache] | Fetch returns the full Markdown in one tool response; no refs, paging, replay, or export interface in the shipped extension. [Runtime][b-runtime] |
| Offline and request guards | `PI_OFFLINE` presence blocks provider access; `/deepseek-search-status` needs no provider or model turn and supports UI/headless output; opt-in developer commands invoke the tools directly. Standalone requests reject redirects, cap bodies at 16 MiB, sanitize errors, support cancellation and use a 60-second deadline without automatic retry. [Wiring][c-status], [offline gate][c-web], [provider][c-provider] | No extension-level `PI_OFFLINE` check or status command in the shipped code. Standalone requests support cancellation and up to three 30-second attempts on timeout or HTTP 408/429/5xx; no explicit body cap or redirect rejection, and provider error text may surface. Standalone results carry a request-cost estimate. Server search instead rejects redirects and uses one 60-second attempt. [Runtime][b-runtime], [standalone transport][b-api], [server][b-server] |
| Pi and release evidence | Declares Node ≥22.18 and Pi ≥1.5.2 <2; offline fake-transport/wiring tests, package allowlist, and pinned Pi 1.5.2 smoke for checkout RPC, headless JSON, and extracted archive RPC. Gated release checks the exact tarball; smoke does not exercise registry installation or live APIs. [Manifest][c-pkg], [tests][c-tests], [smoke and limits][c-testing], [release][c-release] | No declared Node engine or Pi peer range. Mocked API tests and a successful manually dispatched Node 24 npm publish; no real-Pi smoke or exact-archive verification shown in that workflow. The publish run is not evidence of Pi or live provider compatibility. [Manifest][b-pkg], [tests][b-tests], [workflow][b-publish], [run][b-run] |

**Takeaways.** The shared workflow is search → fetch a selected URL → cite, but the tool names and result contracts are not drop-in replacements. bxff offers domain arguments, optional model-mediated search, and full Markdown in one call; cltec uses bounded previews and session retrieval, so reading a long page can take extra calls. **On the public npm registry, `pi install npm:pi-deepseek-search` names bxff's package, not this checkout.** For cltec, the pinned README documents `pi -e ./src/index.ts`. This comparison did not attempt either install path or make live provider calls. [bxff usage][b-readme], [registry identity][b-npm], [cltec usage][c-start], [cltec read contract][c-retrieval]
